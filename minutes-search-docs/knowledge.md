# knowledge.md: instructions for the build agent

You are building **Minutes Search**: a private, sign-in-only web app that mirrors every UK council
document in the Council Gateway API, cleans and summarises it with AI, and lets invited
organisations search it, read it and save searches that send alerts.

This file is the contract. Read it fully at the start of every session. When anything here conflicts
with your own habits or defaults, this file wins. When it conflicts with a doc in `docs/`, this file
wins and you flag the conflict in `PROGRESS.md`.

---

## 2. Golden rules

1. **The Council Gateway API is the only data source.** No CSV files, no scraping council websites.
2. **Users never wait on the upstream API.** The web app reads only our Postgres. Only the pipeline
   worker calls the Council Gateway API.
3. **Raw data is immutable.** Store every upstream response and text exactly as received, with a hash.
   All cleaning is a re-runnable function of raw data plus `PIPELINE_VERSION`.
4. **Nothing half-processed is visible.** A document appears in search, briefings or alerts only when
   `stage = 'published'`.
5. **Never trust upstream fields blindly.** Dates, links, types and names are validated and corrected
   as specified in `docs/04-data-pipeline.md`. Never use `/meetings/{id}` to list a meeting's documents.
   Never use the upstream `/search` endpoint for product search.
6. **Every AI statement is cited and verified.** No summary is stored unless its citations and numbers
   pass the checks in `docs/07-ai-summaries.md`.
7. **Every page and route requires a session**, except the public auth pages listed in
   `docs/08-auth-and-onboarding.md`. Check permissions in the data-access layer, not only in middleware.
8. **Small, verified steps.** One task from the build plan at a time. Each ends with green checks
   (section 5) and an updated `PROGRESS.md`.
9. **Do not invent.** If a library API, model ID, extension or price is uncertain, check the official
   docs, then record what you found in `PROGRESS.md` under "Verified facts". If you cannot check it,
   build behind an adapter and leave a clear TODO with the question.
10. **No silent scope changes.** Anything outside the MVP scope in `docs/01-product-spec.md` needs a
    note in `PROGRESS.md` under "Proposals". Do not build it.

## 3. Stack (settled; see `docs/15-decisions.md`)

- **Language:** TypeScript everywhere, `strict: true`, no `any` except at typed boundaries with a comment.
- **Monorepo:** pnpm workspaces + Turborepo.
- **Web:** Next.js (latest stable, App Router, React Server Components, server actions), Tailwind CSS,
  shadcn/ui, `nuqs` for URL state.
- **Auth:** Better Auth with the Drizzle adapter and these plugins: magic link, email OTP, organization,
  admin, passkey, two-factor.
- **Database:** Postgres. Neon in preview, staging and production; Docker Postgres 17 locally.
  Drizzle ORM with the schema in code and migrations generated by drizzle-kit.
- **Jobs:** pg-boss inside the same Postgres. No Redis.
- **AI:** Anthropic Claude API. `claude-haiku-5-5` for bulk work through the Message Batches API;
  `claude-sonnet-5-5` for on-screen result digests. Model IDs live in one config file.
- **Email:** Resend + React Email.
- **Validation:** Zod at every boundary (env, HTTP input, upstream API responses, LLM output).
- **Tests:** Vitest (unit, integration against a real Postgres), Playwright (end to end), axe (accessibility).
- **Errors:** Sentry. **Hosting:** Vercel (Pro) for the web app and cron-driven workers.

Pin exact versions in `package.json` once installed. Use the latest stable releases at install time
and record the versions in `PROGRESS.md`.

## 4. Repository layout

```
apps/web/                 Next.js app (UI, route handlers, server actions, cron drain route)
packages/db/              Drizzle schema, migrations, seed, data-access layer (dal/)
packages/gateway/         Typed Council Gateway client (generated types + Zod + rate limiter)
packages/pipeline/        Job handlers and pure cleaning functions (no Next.js imports)
packages/ai/              Prompts, output schemas, validators, batch client, eval runner
packages/search/          Query builder shared by search UI and alert matching
packages/email/           React Email templates and send helpers
packages/ui/              Shared UI components (shadcn-based)
packages/config/          eslint, tsconfig, tailwind presets
scripts/                  worker entry point, one-off maintenance scripts
docs/                     This specification
```

Rules: `packages/pipeline` functions that clean or classify must be **pure** (input in, output out, no
I/O) so they are unit-testable against `docs/reference/text-samples/`. Side effects live in job handlers.

## 5. Commands and the definition of done

Create these scripts in the root `package.json` in the first task and keep them working:

```
pnpm dev            # web app on localhost:3000
pnpm worker         # long-running pipeline worker (same handlers as the cron drain route)
pnpm db:up          # docker compose up -d postgres
pnpm db:migrate     # apply migrations
pnpm db:seed        # real pipeline against the API for 3 councils (see docs/13)
pnpm typecheck      # tsc --noEmit across the workspace
pnpm lint           # eslint, zero warnings allowed
pnpm test           # vitest (unit + integration)
pnpm test:e2e       # playwright
pnpm eval:pipeline  # golden-set check for cleaning and classification
pnpm eval:ai        # golden-set check for summaries (uses recorded fixtures unless ANTHROPIC_API_KEY set)
pnpm check          # typecheck + lint + test, the minimum before every commit
```

**A task is done only when all of these are true:**

- [ ] Its acceptance criteria in `docs/14-build-plan.md` are met and demonstrated (test or command output).
- [ ] `pnpm check` passes. Relevant `test:e2e` and `eval:*` suites pass.
- [ ] New logic has tests: pure functions have unit tests; jobs and DAL have integration tests.
- [ ] No TODOs without an owner question in `PROGRESS.md`.
- [ ] Docs updated if behaviour differs from the spec (and the difference is noted in `PROGRESS.md`).
- [ ] `PROGRESS.md` updated: task ticked, short log line, any verified facts or open questions.
- [ ] One commit per task, Conventional Commits style (`feat(pipeline): segment agenda items`).

## 6. Coding conventions

- Functions small and named for what they do. Prefer pure functions; inject clock, fetch and DB.
- Server code only in server files (`import 'server-only'`). Never expose secrets to the client.
- All DB access through `packages/db/dal/*`. Every DAL function takes the acting user (or `system`)
  and enforces access rules. UI code never imports the Drizzle client directly.
- All upstream API calls through `packages/gateway`. It parses every response with Zod, applies the
  rate limiter and retries, and logs to `fetch_log`.
- All LLM calls through `packages/ai`. Never call the Anthropic SDK elsewhere.
- Times are stored in UTC (`timestamptz`); dates displayed in Europe/London. Use `date-fns-tz`.
- Money is stored in pence as integers.
- UK English in all user-facing copy ("organisation", "summarise"). Copy rules in `docs/10-ux-spec.md`.
- Errors: never swallow. Log with context, rethrow or return a typed error. User-facing errors are
  plain-language and say what to do next.
- Feature flags via env (`SEARCH_RANKER=bm25|tsrank`, `AI_ENABLED=true|false`).

## 7. Never do

- Never call the Council Gateway API from a page, component or user request path.
- Never page deeper than page 200 on any upstream list endpoint (deep pages take 30–60 s).
- Never exceed 8 concurrent upstream requests or 10 requests per second.
- Never delete raw data to "fix" a record. Re-run stages instead.
- Never render AI or document text as HTML. Snippets may contain only `<mark>` tags, sanitised server-side.
- Never send user emails, names or profiles to the Claude API.
- Never commit secrets or real user data. `.env.example` lists every variable with a comment.
- Never mark a task done with failing or skipped tests.
- Never change a prompt, cleaning rule or ranking weight without running the matching `eval:*` suite
  and recording before/after scores in `PROGRESS.md`.

## 8. When you are unsure

1. Look in `docs/` (search for the term).
2. Look at `docs/reference/` for real data.
3. Check official library docs.
4. Choose the simplest option that keeps rules 1–10 true, build it behind a small interface,
   and write the question in `PROGRESS.md` under "Open questions".
